# 性能与体验优化记录（2026-10-11）

## 项目理解

这是面向情侣的 Flutter Android 应用，使用 Supabase Auth、PostgreSQL 和 RLS。客户端以 AuthService 管理登录状态、CoupleService 管理情侣空间，Points/Mall/Deposits Repository 管理数据与内存缓存。四个底部页是心意、爱情旅程、心意商城和我的；支持 Firebase 通知、Shorebird 补丁和蒲公英整包更新。

实际登录方式为邮箱和密码。情侣双方通过邀请码共享空间，记录心意、兑换奖励和管理定期心意值。空间与账号隔离、金额口径和失败恢复是优化时的约束。

## 登录超时的判断边界

用户报告 `/auth/v1/token?grant_type=password` 出现 SocketException Connection timed out。这说明客户端没有及时建立/完成连接，不能据此判断密码错误。

本次在开发电脑检查同一个项目域名：无密钥请求健康接口得到 HTTP 401，带客户端公开密钥得到 HTTP 200。一次直接连接约 0.28 秒，另一次带密钥检查约 1.25 秒。这些是单次连通性检查，不代表手机网络、登录接口性能或长期服务可用性。

客户端能够减少多余等待、取消超时请求和改善恢复体验。如果手机网络持续无法连接该域名，仍需比较 Wi-Fi/移动网络、检查该项目可用性与 DNS/网络链路；本次没有擅自替换后端地址或关闭 TLS 校验。

## 已落实的变更

| 方面 | 原行为 | 新行为 |
| --- | --- | --- |
| 首屏 | 显示界面前等待 Firebase 初始化、通知授权等步骤 | 立即显示准备界面，只等待 Supabase 本地会话恢复；初始化失败可重试 |
| 启动流程 | 固定等待 1.2 秒、更新检查、最多三次默认账号登录、绑定查询 | 依据本地会话直接进入登录或首页，后台检查更新与同步绑定 |
| 登录 | 密码请求成功后再请求 getUser；网络错误可能直接展示底层异常 | 使用密码接口返回的用户/会话；中文错误与重试，保留输入，支持自动填充和键盘提交 |
| 网络 | 使用系统连接等待；统一读取最多等待 63 秒；写调用超时后底层还可能完成 | 原生连接超时 6 秒、单个 HTTP 请求总期限 12 秒，传输层取消；读取只对非超时网络失败重试一次，登录/写入不自动重试 |
| 空间同步 | 初始化、登录事件、手动刷新可重复查询；旧账号响应可晚到 | 同账号并发查询合并；返回前校验账号和请求代次；失败与未绑定分开显示 |
| 首页/商城 | 多个独立查询串行等待 | 首页最多 8 个、商城最多 4 个独立读取并发执行；相同缓存键的请求合并 |
| 缓存 | 失效后，旧响应可能重新写入缓存 | 失效时解除旧请求的缓存所有权，防止写操作/退出登录后回填旧结果 |
| 页面体验 | 刷新时整页消失；失败可能显示为零值/暂无记录 | 保留同账号已有内容，说明刷新失败；首次失败提供重新加载按钮 |
| 账号/绑定变化 | 商城、旅程可能不重新加载 | 三个业务页响应账号、空间和伴侣变化，清除旧数据并加载；旧请求不覆盖新页面 |
| 实时更新 | 每个事件立即刷新，订阅范围未限定空间 | 按空间订阅，350 毫秒合并事件；补充定期余额变化刷新 |
| 旅程分页 | 加载更多重新获取前 40/60/80…条 | 每次最多获取下一页 20 条，按时间和 id 稳定排序，合并去重并显示加载完成 |
| 时间筛选 | 结束日的午夜可能排除当天记录 | 包含结束日整天 |
| 通知 | 启动时请求权限，重复 Firebase 初始化 | 初始化合并；进入有效情侣空间后在后台授权/注册设备；拒绝或失败不阻塞主流程 |
| 监听生命周期 | 网络监听未取消，前台推送可能重复订阅 | 网络监听随组件释放，前台推送只订阅一次 |

12 秒是客户端等待上限，不是服务响应速度承诺。网络超时的写入仍可能已被服务端处理；禁止自动重放，实际结果应以刷新后的服务端数据为准。

## 继续验证与优化的优先级

1. **P0：手机网络复测。** 相同版本、相同账号，分别测试 Wi-Fi 和移动网络；覆盖新登录、已有会话、会话过期、断网和恢复网络。记录首次可交互、首页内容可见、登录成功/失败耗时和错误类别，分别统计冷/热启动与 P50/P95。当前没有测量数据，不能给出速度提升百分比。
2. **P1：后端聚合与索引。** 当前累计心意、兑换、定期本金仍由客户端汇总 REST 返回的行。记录增长后，应迁移到受 RLS/权限保护的数据库聚合，并验证 API 行数限制对金额完整性的影响；针对空间、用户、时间的访问检查索引和执行计划。本次没有修改生产数据库。
3. **P1：更大的列表与筛选。** 首页仍展示最近最多 200 条记录，旅程采用分页；持续增长时可增加首页分页、服务端搜索和懒构建时间轴。分页期间出现插入/删除时，offset 页可能移动；已去重，刷新可重建列表，下一步可改用游标分页。
4. **P2：离线与通知。** 当前缓存仅在内存，重启后不能离线查看历史。持久缓存需要按账号/空间隔离并标明同步时间；推送开关、token 更新和通知跳转也应单独完善。

以上后续事项是本次审查识别出的演进方向，不是已交付功能。
