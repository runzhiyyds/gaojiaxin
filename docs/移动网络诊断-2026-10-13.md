# 移动数据连接失败诊断（2026-10-13）

## 结论与证据边界

当前手机移动网络下，对 `supabase.co` 根域名和项目域名的 TLS 握手发生域名相关的连接重置，失败发生在 HTTP/登录请求发送之前。相同手机在 Wi-Fi 下成功，相同目标 IP 上其他域名在移动数据下成功，切回移动数据后故障再次出现。

这强烈支持域名/SNI 相关的网络路径问题，不能单凭这些测试认定是某运营商、国家网络设备或 Supabase/Cloudflare 某个策略发出的重置。未抓取 TCP 重置包来源，也未读取服务提供商的 TLS 边缘日志。

本次使用 Android 系统网络栈独立复现，未重新安装 APP、提交密码登录请求或修改用户数据。TLS 完整握手测试保留证书链和主机名校验。首记录探针只发送 ClientHello 并观察服务器是否开始响应，不用于业务通信。

## 已完成的实测

- 手机：NOH AN01，Android 12；默认网络确认为 CELLULAR，系统标记互联网已验证。运营商属性为 China Mobile（双卡属性均显示该名称）。
- DNS 返回两个地址：`172.64.149.246`、`104.18.38.10`。
- 两个地址的 TCP 443 均能建立连接；项目域名的默认 TLS 模式和强制 TLS 1.2 均被重置。
- 在同一 IP `172.64.149.246` 上切换 TLS 主机名，`supabase.co` 被重置；`supabase.com` 和 `developers.cloudflare.com` 都通过证书校验、完成 TLS 1.3，并返回 HTTP 200。
- 临时开启手机已保存的 Wi-Fi，项目域名在两个地址上都完成 TLS 1.2/1.3，健康接口返回预期的未鉴权 HTTP 401。
- 恢复原来的 Wi-Fi 关闭状态，移动数据下相同故障再次出现。
- 电脑同一 IP/各域名 TLS 均成功；携带本地公开客户端密钥访问项目 Auth health/settings 均返回 HTTP 200（约 0.6/0.4 秒）。未输出密钥或响应正文。

### 移动数据下，固定相同 IP 的首 TLS 记录对照

| TLS 主机名 | 发送 ClientHello 后的结果 |
| --- | --- |
| `uebeyflmmpesjolcrhnp.supabase.co` | 16 ms 后 Connection reset，收到 0 字节 |
| `supabase.co` | 21 ms 后 Connection reset，收到 0 字节 |
| `supabase.com` | 318 ms 后收到 TLS handshake 记录头 |
| `developers.cloudflare.com` | 318 ms 后收到 TLS handshake 记录头 |

记录类型 22 是 TLS handshake。上表仅观察首记录；完整握手与 HTTP 200 由另一个探针验证。域名间 ClientHello 会有主机名/长度差异，这些结果不能替代服务提供商侧归因。

## 排查后的方案

失败发生在请求到达账号验证与业务查询之前，修改密码、RLS、数据库白名单或提高请求超时不会修复本次故障。Supabase 的网络白名单仅作用于 Postgres/连接池，不作用于 Auth/PostgREST HTTPS API：[官方说明](https://supabase.com/docs/guides/platform/network-restrictions)。

当前是 Supabase Free 套餐，提供的 URL 是默认项目地址。没有证据表明 Free 套餐是此次网络重置的原因。Supabase 平台自身的自定义域名属于付费套餐的付费附加服务：[官方说明](https://supabase.com/docs/guides/platform/custom-domains)；此次独立 Cloudflare 检测入口不使用该附加服务。

已在用户自己的 Cloudflare 账户部署 `tools/cloudflare-network-check` 的只读探针。默认 `workers.dev` 地址在手机移动数据下解析到与可信 DoH 不一致的 IP 并失败，电脑使用正确 IP 仍曾握手超时，所以没有将默认地址用于客户端。

用户明确批准“仅新增这个子域名做检测”后，将 `gaojiaxin-check.pet-food-advisor.asia` 绑定同一个只读 Worker。未修改现有产品的根域名记录或路由；操作后的根域名 A 记录和名称服务器与操作前一致。该子域名共用现有注册，无需购买新域名。

手机默认网络 CELLULAR 下实测新入口 `/health`：HTTP 200，耗时 1797 ms，返回 `gatewayReached: true, upstreamReached: true, upstreamStatus: 401`，Worker 上游请求耗时 59 ms。401 是未携带 API Key 的预期健康接口响应，证明两段连接收到了 HTTP 响应，不代表真实登录和数据库鉴权通过。电脑 Dart/curl/浏览器请求标识也通过；较早一次默认 Python 请求出现 403，原因未确定。

业务候选网关已准备但未部署，见 [接入评审](业务入口接入评审-2026-10-13.md)。当前线上入口只读取固定健康接口，不接收/转发账号密码、API Key 或用户 Token。本次未切换 APP 服务地址、未发布新的 APK，APP 移动数据登录尚未完成修复。

## 可复现材料与检查

- Android 探针：`app/tool/network_diagnostics/NetworkProbe.java`（DNS/TCP/完整 TLS/HTTP）、`TLSHelloProbe.java`（首 TLS 记录对照）、`GatewayProbe.java`（实际入口健康响应）。三个源码已通过 Java 8 编译、D8 转换并在手机上运行。
- Cloudflare 只读探针 5 项测试、业务候选 12 项测试通过；两个版本 Wrangler 4.149.0 部署打包 dry-run 通过。只读版本已部署且真机验证；业务候选仅本地测试和打包检查，尚未部署或真实业务回归。
- 诊断不记录手机号码、SSID、用户公网 IP、账号密码、Token 或密钥。
- 若向 Supabase 支持提交问题，提供上述日期、项目引用、运营商属性、两个目标 IP、移动/Wi-Fi/同 IP 主机名对照与失败阶段；请求协助排查 TLS 边缘安全日志。本次失败没有到达 HTTP 层，单看 Auth 登录日志不足以归因。
