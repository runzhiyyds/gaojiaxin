# 项目结构与本质

## 一、项目结构一览

```

├── lib/
```

**设计特点**：按功能分 feature，每个 feature 里「界面 + 该业务的数据访问」；跨业务的「当前用户、空间、对方」由 `AuthService` + `CoupleService` 统一提供，Repository 只认 `coupleSpaceId` / `userId`，不关心从哪来的。

## 二、实现逻辑（数据流与决策）

### 1. 启动与路由

```
main()
  → Supabase.initialize(url, anonKey)
  → MultiProvider( AuthService, CoupleService, PointsRepository, MallRepository )
  → LoveStoryApp (MaterialApp.router)

路由 redirect 规则：
  / (Splash)     → 不拦，交给 Splash 自己跳
  未登录         → 只允许 /login、/register，否则去 /login
  已登录         → 不允许 /login、/register，一律先到 /bind
  /bind、/home/* → 已登录即可访问
  其它           → 兜底到 /home
```

Splash 里实际决策：

1. 可选：Shorebird 检查更新并拉取。
2. 未登录 → `context.go('/login')`。
3. 已登录 → `CoupleService.refresh()` 拉当前用户的 profile、空间、对方信息。
4. `couple.isBound` 为 true → `/home`；否则 → `/bind`（创建空间或填邀请码）。

也就是说：**是否登录** 由 Supabase Auth 决定；**是否进入主 App** 由「是否已绑定情侣空间」决定。

### 2. 绑定关系（情侣空间）——一切业务的前置

- **数据来源**：`profiles.couple_space_id`、`profiles.invite_code`，以及 `couple_spaces` 表的 `user_a_id` / `user_b_id`。
- **CoupleService** 在登录后 `_loadBinding()`：
  - 读当前用户的 profile → 得到 `couple_space_id`、`invite_code`；
  - 若有空间，再查 `couple_spaces` 得到 `user_a_id`、`user_b_id`，从而得到 **partnerId**（对方）。
- **创建空间**：插入 `couple_spaces(user_a_id=当前用户)`，再更新 `profiles` 的 `couple_space_id` 和 `invite_code`；创建后可选初始化一个默认积分项目。
- **加入空间**：不直接改表，而是调 Supabase 的 **RPC `join_by_invite_code`**，服务端校验邀请码、是否已加入、是否自己的码等，再写 `couple_spaces.user_b_id` 和对方的 `profiles`。这样避免 RLS 与并发下的状态错乱。

之后所有业务都建立在「当前用户 + coupleSpaceId + partnerId」之上。

### 3. 积分线（记一笔 → 总额 → 兑换余额）

- **记一笔**：`PointsRepository.addRecord(coupleSpaceId, userId: partnerId, ...)`，即积分记在 **TA** 身上；无 partner 不提交。
- **首页主数字**：本周期 **TA** 的积分（`partnerTotal`），来自 `getCycleTotals(spaceId, period)` 里 partner 的汇总。
- **积分 Tab 主卡**：「TA 的爱情积分」= TA 的累计获得 `getTotalPointsEarned(spaceId, partnerId)`；「TA 的兑换余额」= 该累计 − TA 的兑换消耗 `getTotalPointsSpent(spaceId, partnerId)`。
- **商城**：商品按 `owner_id = partnerId` 展示（即 TA 的商城）；兑换时扣的是 **TA** 的积分（余额 = TA 总额 − TA 已兑换），逻辑已在 Mall 侧按「当前用户」查余额时用 TA 的 earned/spent 体现。

数据表：`point_items`（项目）、`point_records`（每笔记录，含 `user_id`）；统计都在客户端或 Repository 内用 Supabase 查询聚合，没有单独「余额表」。

### 4. 商城线（商品 → 兑换 → 记录）

- 商品表 `mall_goods`：`couple_space_id`、`owner_id`（谁的商城）；兑换表 `exchange_records`：`user_id`（谁扣积分）、`points_spent`。
- 展示：只查 `owner_id = partnerId` 的商品；兑换时校验「TA 的余额 ≥ 商品所需积分」后写入 `exchange_records` 并扣库存。

整体上，**积分** 和 **商城** 都围绕「空间 + 谁获得 / 谁消耗」在 Supabase 里完成读写，Flutter 只做调用与展示。

## 三、Supabase 在项目中的地位（洞穿本质）

### 一句话

**Supabase 是这个 App 的唯一天然后端：既管「谁」（Auth），又管「数据往哪存、谁可以动」（Postgres + RLS），还管「绑定关系里不能乱写」的复杂写逻辑（RPC）。**

### 拆开说

| 能力 | 在项目中的用法 | 本质 |
|------|----------------|------|
| **Auth** | 邮箱注册/登录、Session、`currentUser.id` | 所有「当前用户」的来源；RLS 里 `auth.uid()` 的根据。 |
| **Postgres** | profiles、couple_spaces、point_items、point_records、mall_goods、exchange_records | 业务数据唯一落库点；没有第二个数据库或自建 API。 |
| **RLS（行级安全）** | 每张表 policy：只能动「自己」或「自己所在空间」的行 | 保证即使用 anon key 调接口，用户也只能在约定范围内读写，不会越权。 |
| **RPC** | `join_by_invite_code`：校验邀请码、写 user_b、更新 profile | 把「加入空间」做成一个原子操作，避免客户端多步写导致状态不一致。 |

所以：**没有 Supabase，这个 App 就没有用户体系和持久化；换掉 Supabase，就等于换掉整个后端。** 前端（Flutter）只做三件事：用 Supabase 的 SDK 登录、按业务调表/RPC、根据 CoupleService 提供的 spaceId/partnerId 决定「给谁记、显示谁、扣谁的余额」。

### 数据流简图（本质关系）

```
                    ┌─────────────────────────────────────┐
                    │           Supabase                   │
                    │  ┌─────────┐    ┌─────────────────┐  │
  Flutter App       │  │  Auth   │───▶│ auth.uid()      │  │
  ─────────────     │  │ (登录)  │    │ 给 RLS 用       │  │
                    │  └─────────┘    └────────┬────────┘  │
  AuthService ─────┼──▶ Session/User           │           │
  CoupleService ───┼──▶ profile + couple_spaces │           │
                   │    → spaceId, partnerId   │           │
  PointsRepo   ────┼──▶ point_* 表 ◀───────────┘           │
  MallRepo     ────┼──▶ mall_* / exchange_*   (RLS 限制)   │
                   │  RPC: join_by_invite_code              │
                    └─────────────────────────────────────┘
```

- **上：** 所有「是谁」都来自 Auth；所有「能看/能改什么」都由 RLS 根据 `auth.uid()` 和空间关系决定。
- **下：** 业务只认 `spaceId` + `userId`/`partnerId`，不关心这些 id 是从哪来的；Repository 只是「带鉴权的 Supabase 客户端封装」。

## 四、总结（洞穿本质）

1. **项目结构**：单 Flutter 应用，按 feature 划分；核心状态是「当前用户 + 当前空间 + 对方」，由 Auth + CoupleService 提供，其余都是「在这个空间下对积分/商城的 CRUD」。
2. **实现逻辑**：登录 → 绑定（创建或加入空间）→ 主框架内使用「TA 的积分 / TA 的商城 / 记给 TA」；积分与商城的数据流都围绕 `couple_space_id` 和 `user_id`/`owner_id`，在 Supabase 内完成。
3. **Supabase 的地位**：**唯一后端**——身份、数据、权限、关键写逻辑（如加入空间）全部在 Supabase；App 是「带 UI 的 Supabase 客户端」，没有独立业务服务端。

如果你后续要加「推送、统计、风控」等，要么继续用 Supabase 的扩展（Edge Functions、Realtime），要么在 Supabase 之外再接一层服务；但就当前功能而言，本质就是「Supabase 驱动一切，Flutter 负责展示与交互」。
